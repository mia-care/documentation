## September 2026 (v3.5.1)

### P4SaMD v3.5.1, 9 September 2026 (patch)

A patch release that completes the Verification safety alert feature 3.5.0 introduced: alerts are now raised automatically from test results and coverage, instead of only being acknowledgeable. It also shows traceability coverage on each unit test report, removes a limit that hid older test runs, and extends content-based file checking to project imports.

<FeatureGrid>

<FeatureBox icon="🚨" title="Automatic Safety Alerts">

Verification now raises a safety alert on its own when a failed test result or a coverage gap affects a safety-relevant part of your system. Alerts are advisory and never block a report, its review, or its approval.

</FeatureBox>

<FeatureBox icon="📊" title="Coverage On Every Report">

Each unit test report now shows how much of its own test population carries verification traceability, next to the gaps it already listed.

</FeatureBox>

</FeatureGrid>

:::info Safety alerts start appearing after this upgrade
Until now the safety alert list on a unit test report was always empty, because nothing raised alerts. After you upgrade, reports meeting the conditions below will show a safety alert banner. This is expected rather than a regression: alerts are advisory, they never block report upload, review, or approval, and the upgrade changes no existing report data. Acknowledging an alert still requires a written justification and is still recorded in the audit log.
:::

#### New: safety alerts are raised automatically

Release 3.5.0 added acknowledgement but left the raising of alerts to a later release. This release delivers it.

A safety alert is raised for a test case and the software item it verifies when either of these holds:

- the test case has a **Failed** or **Error** result, or
- the run's line coverage or branch coverage is below the threshold for the software item's safety class: **100%** for Class C, **80%** for Class B, **60%** for Class A.

A run that reports no coverage figures raises no coverage alert. The two conditions are independent, so a failed test case on an item that is also below its coverage threshold raises two separate alerts.

Only software items that are **Class C**, or that are linked to a risk control measure, are considered at all. An item classified as not medical device software is never considered, even when it is linked to a risk control measure.

Alerts are kept current automatically. They are re-evaluated when a new test report is uploaded, when a software item's safety class changes, when a risk control measure link is added or removed, when a traceability link between a test case and a software item is added or removed, and when a linked test case or software item is deleted. An alert clears on its own once its condition no longer holds, and the record is retained for audit history.

An acknowledged alert stays visible until its underlying condition clears. Acknowledging is a documented decision, not a way to dismiss the warning.

#### New: traceability coverage on each unit test report

A unit test report now reports its own traceability coverage: how many of its active test cases carry a verification traceability link, out of how many, as a percentage. This sits alongside the traceability gap list reports already showed, and the two always agree because they are computed from the same test population.

This is a different measure from the traceability coverage on the Verification dashboard, and the two can legitimately differ:

- The **per-report** figure counts only verification links, and is shown for every report whatever its approval status.
- The **dashboard** figure counts any traceability link, including a link only to a risk or a control measure, and covers approved reports only.

A test case whose only links are to risks therefore counts towards the dashboard figure but not towards its own report's coverage.

#### Improved: the full unit test run history is reachable

The run list was capped, so a workspace with a long history could not reach its older runs at all. The list is now paginated properly and the whole history is browsable. Run rows also show the current name and status of the workspace version they belong to.

#### Improved: file checks when importing an existing project

Files attached in the import wizard are now validated by their actual content, not only by their file extension and declared type. A file whose contents do not match the format its extension claims is refused, as is a file carrying executable content. This extends to project imports the check release 3.5.0 applied to System Design files.

The wizard also checks a file as soon as you pick it, rather than only when you submit the step, so a file that cannot be accepted is reported straight away instead of several steps later. The checks performed on submission remain the ones that decide.

#### Improved: switching organization from the collapsed sidebar

You no longer have to expand the sidebar to switch organization. The switcher is available directly while the sidebar is collapsed.

#### Fixed

- A test case linked to a work item with any traceability relationship now counts as traced in a run's traceability gaps. Previously only one specific relationship counted, so a test case linked in another way was reported as an open gap it had already closed. Links to risks and control measures still do not count as verification, so a test case whose only links are to risks continues to be reported in the safety-relevant tier, as risk control verification requires.
- Editing a control measure no longer resets the relationship type on its linked items. Opening a control measure and saving it previously replaced the relationship you had chosen with a default. Link relationships are also now read in both directions, so a link created from the other end is no longer invisible to the control measure it belongs to.

#### For developers

- The safety alert payload on a unit test run summary has changed. It previously carried a severity and a message, and was always empty. It now identifies the triggering test case and software item, that item's safety class, whether the item is linked to a risk control measure, why the alert was raised, when it was raised, and its acknowledgement state with author, timestamp, and justification. Any integration reading the old severity or message fields needs updating.
- A unit test report now carries its own traceability coverage counts and percentage, distinct from the project-level figure described above.
- A new endpoint validates an import file against the same rules the real upload applies, without a session and without storing anything, so a client can check a file before committing to an upload. The type catalogs also report which file extensions are refused outright.

#### Upgrade notes

- **Deploy backend and frontend together.** The safety alert payload is a shared contract between them. Running an older frontend against this release shows safety alert banners with no message and no severity, which means a safety warning that cannot be read.
- **Expect safety alert banners** on unit test reports that meet the conditions above, as described in the note near the top of this section. Nothing is blocked and no report data changes.
- **Some import file uploads that previously succeeded may now be refused**, because files are checked against their actual content. This is the intended result of the file-validation work, and it may affect an existing import routine that relied on a file whose extension did not match its contents.

## August 2026 (v3.4.0 to v3.5.0)

### P4SaMD v3.5.0, 26 August 2026

Version 3.5 realigns the risk matrix with ISO 14971:2019 terminology and closes the confirmed findings from a recent third-party penetration test. It also loosens System Design item typing, adds safety-alert acknowledgement to Verification, and fixes the most-reported cause of a stuck requirement quality score. **This release requires regulatory/QA review before promotion in regulated environments**, because it reclassifies existing risk records.

<FeatureGrid>

<FeatureBox icon="⚠️" title="Risk Matrix Realignment">

The risk level matrix now follows the ISO 14971:2019 "Option A" 5×5 matrix. Existing risks are recomputed automatically, and some severity/probability combinations that were previously **Unacceptable** are now **Tolerable**. This is a genuine reclassification, not a relabelling.

</FeatureBox>

<FeatureBox icon="🔒" title="Security Hardening">

Fixes for two confirmed findings from a penetration test targeting design-file rendering and upload: a stored script-execution issue in rendered design content, and insufficient validation of uploaded file content against its declared type.

</FeatureBox>

</FeatureGrid>

:::caution Existing risk records are reclassified: review before promoting
This release renames the risk zone previously labelled **ALARP** to **Tolerable**, and replaces the risk matrix's severity/probability boundaries with the ISO 14971 "Option A" matrix. Every existing risk in your Risk Management File is automatically recomputed against the new matrix when you upgrade. Some risks that were previously classified **Unacceptable** are now classified **Tolerable**, including Severity 5/Probability 1, Severity 4/Probability 2, and Severity 3/Probability 3 combinations. This can change risk-control obligations for records that already exist, so have your regulatory/QA function review the change before promoting this release. Every reclassified risk gets its own history entry and audit log entry.
:::

#### Breaking: the ALARP risk zone is renamed to Tolerable

Per ISO 14971:2019 terminology, the risk zone formerly labelled **ALARP** is now called **Tolerable** everywhere in the platform: the risk level shown on a risk, risk list filters and summary cards, CSV import/export, error messages, and the MCP tool catalog. `ALARP` is no longer a valid value anywhere.

You can still customize how the three zone names are displayed for your project from the Project Customization settings, but the underlying computation always uses the canonical **Acceptable / Tolerable / Unacceptable** zones.

**If you or a connected tool call the P4SaMD API or MCP tools directly:** any integration that sends or filters on `ALARP` must be updated to use `Tolerable`. Filtering by an unrecognized risk level now returns a clear error naming the three valid zones instead of silently returning no results.

#### Regulatory: risk matrix realigned to ISO 14971 "Option A"

The risk level (initial and residual) is now computed from the ISO 14971:2019 "Option A" 5×5 severity/probability matrix, applied consistently everywhere a risk level is shown or computed. Every existing risk's initial and residual risk level is recomputed once, automatically, during the upgrade (see the caution note above). This is a one-time, one-way update: there is no option to view risks under the previous matrix afterward.

#### New: flexible System Design item types

A System Design item's type (System, Software Item, Software Unit, or SOUP) can now be changed after creation. The change is checked against the item's parent and existing children, and is rejected if it would leave the hierarchy in an invalid state.

#### New: Verification safety alerts

Verification can now raise a safety alert against a unit test report. A safety alert must be explicitly **acknowledged**, with a written justification, before it is cleared. Every acknowledgement is recorded in the audit log. (Raising alerts automatically from evaluation results is planned for a future release; this release adds acknowledgement only.)

#### Improved: Verification and traceability

- Unit test reports now always show the current name and status of their workspace version, even for older reports, instead of the name captured when the report was uploaded.
- A test run's test cases can now be linked to multiple target types (for example, several software items and requirements) in a single submission, with a summary panel showing what was linked.
- Traceability links between test cases that sit at different test levels are no longer allowed, to keep the traceability matrix consistent.

#### Improved: Organization plan limits

Your organization's user and project limits are now resolved the same way everywhere they're enforced or displayed. The invitation flow, project creation, the seats counter, and the Information tab always agree, resolving any per-organization override first, then your subscription tier, then the free-tier default.

#### Fixed: the stuck "Evaluating…" quality score is resolved

Requirement quality score is the most-reported issue fixed in this release. It had two separate causes:

- Editing a requirement no longer wipes its quality score unless the change touches requirement content (description or acceptance criteria). A status change, reassignment, re-parenting, or reordering no longer clears an existing score or triggers an unnecessary re-evaluation.
- Every quality-score evaluation the platform accepts now reaches a final state, so a report no longer gets stuck showing **Evaluating…** indefinitely. If the AI evaluator can't complete it, you see a failure you can retry.

#### Fixed

- The requirements list keeps a stable order across unrelated updates, and always reflects the sort order actually applied.
- Re-selecting a value that was already set on a requirement (for example, in a dropdown) no longer records a spurious edit in its history.
- The unsaved-changes warning on a requirement's detail page now only applies to the Description and Acceptance Criteria fields; other fields save automatically as you edit them.

#### Security: penetration-test remediation

Following a third-party penetration test, this release closes two confirmed findings affecting design files:

- **Stored script execution in rendered design content.** Design-file content, previews, and diffs are now rendered through a single hardened Markdown renderer across the whole application, and the platform's content-security policy no longer allows inline or `eval`-based script execution. This closes a path where design-file content containing a crafted script could execute in another user's browser.
- **Insufficient validation of uploaded design files.** Uploaded design files are now validated against their actual byte content, not just their file extension or the browser-reported file type. A renamed executable, for example, is rejected instead of accepted as a text or markdown file. Rejected uploads get a generic error that doesn't reveal why validation failed. Downloaded design files also carry an additional protective header, and filenames with accented or non-ASCII characters now download with the correct name.

#### For developers

- The MCP tool catalog grows from 36 to 40 tools, adding SBOM download and unit test case management (`download_sbom`, `list_test_cases`, `get_test_case`, `create_test_case`).
- The risk-level query parameter and MCP schemas now validate against `Acceptable`, `Tolerable`, and `Unacceptable` only, returning `400 invalid_query_parameter` with the allowed values for anything else.

#### Upgrade notes

- **Deploy backend and frontend together.** The `ALARP` → `Tolerable` rename is a shared contract between them; running mismatched versions can show blank or unmatched risk-zone labels.
- **Back up your database before upgrading.** The risk matrix realignment rewrites existing risk records in place, and this step cannot be reversed. For a large Risk Management File, expect the upgrade to take longer than usual: it writes a history and audit entry for every reclassified risk.

## July 2026 (v3.3.0 to v3.3.1)

### P4SaMD v3.3.0, 9 July 2026

Version 3.3 focuses on administrative visibility and evaluation reliability: organization admins get a clearer view of tenant status and plan usage, Product Information now keeps a change history, and both Brownfield and AI-assisted evaluations recover more gracefully from interruptions.

#### New: Organization Information & Plan Overview

The organization **Settings** page is now organized into three tabs: **Information**, **Members**, and **AI Configuration**. All three are still restricted to the **Admin** role. The new **Information** tab shows a Tenant Overview card (organization name and status) and a Subscription Plan card (current plan tier, users and projects in use against your plan's limits).

#### New: Product Information Change History

The **Product** page (**Configuration → Product** in the project sidebar) now has two tabs: **Details** (the existing view/edit form) and **History**. The History tab lists every change made to the product's metadata: product name, description, intended use, safety classification, target market region, regulatory frameworks, and AI-powered type. Each entry shows who made the change and when, and a filter narrows the feed to a single field.

#### Improved: Brownfield Evaluation

- **Retry Evaluation** is now available on a failed evaluation. Open the failed session's Evaluation page and click **Retry Evaluation** to resubmit the same materials for a fresh evaluation without redoing the wizard.
- The gap analysis now surfaces a normative reference for more gaps, drawing on additional regulatory metadata (such as the specific article or regulation) supplied by the applicable framework.

:::caution Brownfield evaluation accuracy fix
This release fixes a defect in the Brownfield compliance check where certain gaps could be reported as compliant when they were not. If you rely on a Brownfield evaluation completed before 9 July 2026, re-run the evaluation (using the new **Retry Evaluation** button, or by starting a new session) to get corrected results.
:::

#### Improved: Evaluation Reliability

Requirement quality-score, Brownfield, and Whisper evaluations now recover more predictably from interruptions:

- An evaluation that stalls (for example, because of a slow or unresponsive AI provider) now fails with a clear error after a bounded wait instead of remaining in progress for hours.
- An evaluation left in progress by a platform restart is now automatically detected and marked as failed shortly afterward, instead of appearing to run indefinitely, so you know when it is safe to retry.
- Evaluations are no longer at risk of being incorrectly marked as failed during routine platform maintenance.

#### Fixed

- Resuming a Whisper chat conversation after confirming a proposed action no longer occasionally fails to send your next message.

#### Security

All AI-powered evaluation workloads (Requirement Quality Score, Brownfield analysis, and Whisper compliance suggestions) now use your organization's own configured **Evaluation** credentials end to end for every request. See [AI Configuration](../handbook/ai_configuration.md).

#### For developers

The requirements REST API and MCP tool catalog gained new capabilities for managing requirement hierarchy programmatically: re-parenting a requirement, setting labels and an initial status at creation, endpoints for managing sections, and creating requirement-to-requirement traceability links. These are currently available via the API and MCP only; UI support is planned for a future release.

#### New: Whisper AI Assistant

The Whisper panel slides in from the right (and can be expanded to full page) and shows the current project and version context. Its two modes are:

### P4SaMD v3.1.1, 12 June 2026

A maintenance release that migrated file storage to a managed object store.

#### Changed: File storage migrated to Google Cloud Storage

The self-hosted file storage backend was replaced with a managed **Google Cloud Storage (GCS)** bucket across all environments. This removes a single point of failure (an unreplicated storage pod) and the risk of data loss on restart, and simplifies credential management.

:::warning Breaking change
**Files uploaded before this release are not accessible afterward.** No data was migrated between the old storage and the new GCS bucket, so any previously uploaded files must be re-uploaded, including design files in the System Design section. This was an accepted trade-off given the platform's current internal-only audience and the small volume of stored data.
:::

### P4SaMD v3.1.0, 11 June 2026

Version 3.1 deepens the native SDLC artifact management introduced in v3.0, with a focus on the **System Design** workspace, formal lifecycle controls, and team administration.

#### New: Software Item Lifecycle (System Design)

Software items now carry a formal IEC 62304-aligned lifecycle status: **Draft → Approved → Verified**, plus a terminal **Deprecated** state. You move items through the lifecycle from the software item detail view:

- **Approve** an item once its design is ready (requires the Admin role).
- **Verify** an approved item once it has supporting evidence.
- **Revert to Draft** to reopen an Approved or Verified item for further work.
- **Deprecate** an item that is no longer in use. Deprecation is one-way, requires a written rationale (at least 10 characters), and is only available for items belonging to a released version.

Items that belong to a **released** version are protected: they cannot be deleted, and editing them requires an edit rationale that is recorded in the item's history.

#### New: Tabbed Detail Pages for Requirements and Software Items

Requirements and software items now open in a detail page with three tabs:

- **Details**: view and inline-edit all fields, including the parent/child hierarchy and a system-metadata block (created/updated/approved by, with timestamps).
- **Traceability**: linked risks, tests, software items, and change requests, plus a risk-coverage indicator and a link to the traceability matrix.
- **History**: a chronological audit trail of every create, edit, status transition, and deletion, now showing the human-readable name of the person who made each change.

#### New: Product Members Management

Each project gets a **Members** page (shown as **Product Members** inside a project, **Tenant Members** at the organization level) for managing who has access and at what role. The page includes a member table with search and role filtering, a stats panel, and an **Add Member** dialog with an expandable per-role capability breakdown. Removing a member is guarded so you cannot remove the last Admin. See [Roles and Permissions](../security/roles_permissions.md) for the full role model.

#### Improved

- Requirement and software item lists are now **sortable** and show a stats bar; requirements can be sorted by their display ID.
- Label entry now offers **autocomplete suggestions** instead of a separate single-label filter.
- Larger design files can be uploaded to software items without hitting a size limit.

#### Fixed

- Switching organization now cancels in-flight requests and clears tenant-scoped cached data, so screens no longer briefly show data from the previously selected organization.
- Corrected sort ordering on the Risk and Software Item lists.

#### For developers: extended MCP coverage

The bundled MCP server gained broad new read/write coverage (requirement lifecycle transitions, full risk register management, traceability links, software item browsing, version management, and design-file access), so external AI assistants and coding agents can operate on project data without REST access.

## May 2026 (v3.0.x)

The v3 product line launched in May with v3.0.0, followed by a series of v3.0.x patch updates.

### P4SaMD v3.0.0, 26 May 2026

Version 3.0 is a complete re-architecture of P4SaMD and the beginning of the v3 product line. The platform is standalone and operates independently of any third-party software infrastructure.

#### What's New

<FeatureGrid>

<FeatureBox icon="🏗️" title="Standalone Platform">

P4SaMD v3 runs as an independent product with its own user interface. It no longer requires Mia-Platform Console or any other external platform to be deployed or in use by your organization.

</FeatureBox>

<FeatureBox icon="🔐" title="Federated Authentication">

Authentication in v3 uses a federated OIDC identity provider bundled with the P4SaMD installation. The two-token authentication model (login token plus tenant-scoped token) keeps session management IdP-independent. Switching to a different identity provider in the future requires only a configuration update.

</FeatureBox>

<FeatureBox icon="🏢" title="Multi-Tenant Architecture">

A single P4SaMD installation now serves multiple independent organizations simultaneously. Each organization has complete data isolation from others on the same installation. Users can belong to multiple organizations and switch between them without logging out.

</FeatureBox>

<FeatureBox icon="📝" title="Native Work-Item Management">

Requirements, risks, tests, and change requests are now managed natively inside P4SaMD. An external ALM tool (such as Jira) is no longer required to start using the platform. External ALM integrations remain available as optional bidirectional synchronization features.

</FeatureBox>

<FeatureBox icon="📦" title="Multiple Projects per Organization">

Organizations can now manage multiple medical device software projects in a single P4SaMD instance. Each project has its own team, configuration, compliance context, and version history.

</FeatureBox>

<FeatureBox icon="⚙️" title="Self-Service Configuration">

Organizations and projects can be configured autonomously through the platform interface, without asking Mia-Care to make changes on your behalf. This includes integration setup, workflow configuration, and organizational settings.

</FeatureBox>

<FeatureBox icon="🔄" title="Brownfield Import">

Use the Brownfield Import wizard to onboard existing software projects. A six-step guided workflow collects project context, technical assets, and existing documentation, then triggers an automated compliance gap analysis and generates a prioritized remediation plan.

</FeatureBox>

<FeatureBox icon="📋" title="Requirements Management (v3 Architecture)">

Requirements are now managed as native platform entities with a hierarchical tree structure, lifecycle statuses (Draft → In Review → Approved → Verified), bidirectional traceability, and import/export capabilities. No external ALM synchronization is required.

</FeatureBox>

<FeatureBox icon="📌" title="Version Management">

Workspace versions provide IEC 62304-aligned configuration management. Draft versions support active development; released versions are permanently locked as compliance records.

</FeatureBox>

</FeatureGrid>

#### Upgrading from v2

P4SaMD v3 is a new platform. There is no direct in-place migration path from v2. To move from v2, we recommend using the **Brownfield Import** feature to onboard your existing projects into the v3 platform. Contact Mia-Care for migration support.

### Patch updates: late May 2026 (v3.0.x)

#### New: Risk Management

P4SaMD now includes a full **Risk Management** module compliant with ISO 14971. You can create, assess, mitigate, and track risks directly in the platform with:

- A 5×5 severity/probability risk matrix with automatic risk level computation
- A complete status lifecycle (Identified → Analyzed → Mitigation Required → Under Control → Verified → Accepted)
- Control measures with verification tracking and residual risk documentation
- Bidirectional traceability to requirements and test cases
- CSV import and export for the risk register
- Bulk operations for efficient risk management

See the [Risk Management handbook page](../handbook/risks.md) for full details.

#### Improved: Requirement Quality Assessment

Requirement quality is now assessed automatically every time you create or edit a requirement. Quality badges (Very High, High, Low) update in real time without any manual trigger. While a new score is being computed, the badge is temporarily hidden.

#### Improved: Brownfield Evaluation Pipeline

The Brownfield evaluation now tracks progress in real time through four processing phases (Document Preparation, Extraction, Payload Crafting, Evaluation). After completion, two new metrics are available: **Compliance Health Score** and **Traceability Coverage**. Evaluation results can also be exported in PDF and CSV formats.

#### Improved: Requirements Import

CSV import now gives per-row validation feedback. Valid rows are imported even when other rows contain errors (partial-success behavior), so you no longer need to fix all issues in a file before any requirements are created.

#### Changed: Default Workspace Version Name

New projects now start with a default workspace version named **main** (previously `v1.0`).

#### Patch Fixes

- Fixed requirements type filter where selecting PRS or SRS showed items of the opposite type
- Fixed requirements export where parent display IDs were not resolved correctly when parent items were excluded by filters
- Internal infrastructure and performance improvements
